# Cleanup pass v4 — bugs that were silently lurking

Fourth refactor pass. Different files yet again. Three real bugs found, all of them invisible in normal use but actively wrong.

## Bugs landed this pass

### `TransferProgressSink` name-collision: ADBSession.fetch never satisfied Transport.fetch

`TransferProgressSink` had **two** declarations with the same name:
- `Sources/FreeDroidDomain/Transport/Transport.swift` — a `protocol` with `report(bytesTransferred:totalBytes:)`.
- `Sources/FreeDroidADB/Wire/ADBSyncClient.swift` — a `public typealias` for `@Sendable (Int64, Int64?) -> Void`.

Inside `FreeDroidADB`, the typealias won name resolution, so `ADBSession.fetch(progress: TransferProgressSink?)` had a *closure* parameter. The `Transport` protocol's `fetch` (declared in `FreeDroidDomain`) expected the *protocol* parameter. Different signatures → ADBSession.fetch did **not** satisfy the protocol requirement. The protocol's default extension (a slow chunked-read loop) was bound to the witness instead.

In practice this didn't bite because every real call site reaches `ADBSession.fetch` through a concrete type (the bridge → `ADBSession`). Anyone calling `.fetch` through an `any Transport` reference would silently regress to the slow path.

Fix: renamed the typealias to `WireProgressCallback`, made `ADBSession.fetch`/`upload` accept the protocol, and added `wireCallback(from:)` that wraps a protocol into a closure when calling into `ADBSyncClient`. ADBSession.fetch now actually overrides Transport.fetch.

### MTPSession returned `nil` storage stats so MTP cards had no storage bar

`DeviceInfo.storageCapacityBytes` / `storageFreeBytes` were nil-by-default on the MTP path. The device-card UI already had a tinted storage bar (amber at 85%, red at 95%), but MTP-only devices showed nothing because the values were always nil.

Fix: `MTPSession.info` walks the `LIBMTP_Get_Storage(dev, 0)` linked list, summing `MaxCapacity` and `FreeSpaceInBytes` across all storage volumes (phone storage + SD card).

### AsyncStream continuation leak in three broadcaster actors

`USBDeviceWatcher`, `DeviceRegistry`, and `TransferQueue` each broadcast to subscribers by appending continuations to an array. None set `onTermination`, so when a subscriber stopped consuming (SwiftUI `.task` cancellation, menu-bar re-subscribing, etc.) the continuation stayed in the array. Every event then yielded to all the dead continuations too.

Fix: switched from `[Continuation]` to `[UUID: Continuation]`. Each subscription gets a UUID; `onTermination` unregisters by ID. Dead consumers are reaped immediately.

## Not bugs but worth noting

- `FileBrowserViewModel` is 249 lines and could split, but every responsibility seems coherent (state, navigation, focus, inspect, sort). Leaving alone.
- `WifiADBCoordinator`'s substring match on adb output is fragile, but the actual adb client output uses one of "failed"/"error"/"unable" reliably. Polish task.
- `XPCFileServerHandler` (main-app side) and `BridgeHandler` (appex-side) duplicate the IPC dispatch switch. Tracked under A1 (type-safe IPC) in the v3 plan.

## Forward plan delta

Carrying forward from v3:

1. **F1 (in-app live transfer panel for Finder copies)** — same recommendation: shared-cache JSONL + `DispatchSource` watcher. Half-day, biggest perceived-quality jump.
2. **F2 (cross-device drag-and-drop)** — ~1 day; orchestration on top of wire client.

New items surfaced this pass:

- **Audit ContentCache concurrent-write semantics.** If two `fetchContents` for the same `ContentKey` race, both might call `store`. Both create the same entry directory and write `meta.json` on top of each other. Probably fine but worth checking.
- **`AppContainer` fatal-error on adb-server boot.** If adbd fails to spawn for any reason (e.g., port already in use by another adb instance), the app crashes on launch. Should show a UI error with retry.
- **`FileBrowserViewModel.inspect`** auto-previews files up to 12 MB by downloading them. For users on metered connections this is silently wasteful. Add a setting / threshold.
